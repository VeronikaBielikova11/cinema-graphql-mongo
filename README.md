# Cinema GraphQL API

GraphQL API кінотеатру на NestJS, MongoDB і Mongoose: фільми, зали, сеанси й бронювання місць. Схема будується підходом code-first. REST-контролери та Swagger із попередньої роботи видалено.

## Запуск

Встановлення залежностей:

```bash
npm install
```

Файл змінних оточення:

```bash
cp .env.example .env
```

Приклад `.env`:

```dotenv
PORT=3000
MONGO_PORT=27019
MONGODB_URI=mongodb://localhost:27019/cinema
```

| Змінна        | Опис                                     |
| ------------- | ---------------------------------------- |
| `PORT`        | порт застосунку, за замовчуванням 3000   |
| `MONGO_PORT`  | порт MongoDB на хості для Docker Compose |
| `MONGODB_URI` | рядок підключення до MongoDB             |

Підняття MongoDB через Docker Compose:

```bash
docker compose up -d --wait
```

Заповнення бази тестовими даними (повторний запуск не створює дублікатів):

```bash
npm run seed
```

Запуск у режимі розробки:

```bash
npm run start:dev
```

## GraphQL-ендпоінт

`http://localhost:3000/graphql`

Запити надсилаються методом POST. Поза режимом production за цією ж адресою в браузері відкривається GraphiQL.

Згенерована схема лежить у файлі [`schema.gql`](./schema.gql). Шлях до нього задається параметром `autoSchemaFile` у `src/app.module.ts`, а сам файл оновлюється при старті застосунку.

## Проблема N+1: DataLoader

Обрано DataLoader (`src/loaders/loaders.service.ts`).

Поля `film` і `hall` типу `Showing` розкриваються резолверами полів. Кожен резолвер лише додає ідентифікатор у чергу свого loader-а, а loader за один тік циклу подій збирає всю чергу й робить один запит з `$in`. Сторінка сеансів із вкладеними `film` і `hall` дає один запит за сеансами, один підрахунок загальної кількості, один запит до `films` і один до `halls`, незалежно від розміру сторінки.

Чому DataLoader, а не `populate`:

- `populate` виконувався б завжди, навіть коли клієнт не запитував вкладені поля. Loader звертається до колекції лише тоді, коли поле справді запитане.
- Той самий механізм працює для всіх запитів, що повертають сеанс: списку, одного сеансу й мутації створення.

Результат вибудовується за порядком вхідних ідентифікаторів, бо MongoDB не гарантує порядок для `$in`. Loader-и створюються заново на кожен запит у функції `context`, тому кешовані документи не переходять між запитами різних клієнтів.

## Приклади запитів

Сторінка сеансів із назвами фільмів:

```graphql
query {
  showings(date: "2030-06-15", page: 1, limit: 10, sort: ASC) {
    total
    page
    limit
    items {
      id
      startsAt
      price
      film {
        title
      }
      hall {
        name
      }
    }
  }
}
```

Бронювання місць:

```graphql
mutation {
  createBooking(
    showingId: "653333333333333333333332"
    seats: [{ row: 1, seat: 1 }, { row: 1, seat: 2 }]
  ) {
    id
    totalPrice
    seats {
      row
      seat
    }
  }
}
```

## Бронювання

Зайняття місць і запис бронювання виконуються одним оновленням документа сеансу. Умова оновлення перевіряє, що всі потрібні місця вільні, а результат перевіряється за `matchedCount`. Якщо хоча б одне місце зайняте, документ не змінюється, тому жодне місце зі списку не бронюється.

## Коди помилок

Код помилки міститься в `errors[0].extensions.code`.

| Код                     | Коли повертається                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------- |
| `BAD_USER_INPUT`        | порушено правила валідації, некоректний формат ідентифікатора, місця немає в залі             |
| `NOT_FOUND`             | мутація над неіснуючим документом                                                             |
| `CONFLICT`              | зайняте місце, видалення фільму або залу із залежними сеансами, зал із такою назвою вже існує |
| `INTERNAL_SERVER_ERROR` | непередбачена помилка; деталі йдуть лише в логи сервера                                       |

Запити `film`, `hall` і `showing` для неіснуючого документа повертають `null` без помилки.
